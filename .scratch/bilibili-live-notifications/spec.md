# Bilibili 开播通知

Status: ready-for-agent
Implementation: complete

## Problem Statement

使用者希望在关注的 Bilibili 主播开播时收到 QQ 私聊提醒，无需反复查看直播间。现有系统只能按仓库订阅发送 GitHub Issue 通知与追踪动态，无法监控直播间，也没有供用户自助订阅直播间的入口。管理员需要能够在现有控制台代用户配置，并查看查询或发送异常。

## Solution

增加独立的直播订阅能力：用户通过 QQ 私聊命令订阅任意有效直播间，管理员也可在通知目标编辑界面配置同一份订阅。一个通知目标可以订阅多个直播间，同一直播间的订阅者共享每两分钟一次的检查。

发现新直播场次后，向发现时的订阅者发送包含主播名称、直播标题、房间号及链接的纯文字开播通知。首次订阅已经开播的房间只反馈当前状态，不推送当前场次。逐接收者记录投递结果，支持有限时效内重试、重启去重及退订取消，避免向成功接收者重复广播和向退出者发送积压消息。

## User Stories

1. 作为 QQ 用户，我希望通过 `/bilibili 房间号` 订阅直播间，以便开播时收到私聊通知。
2. 作为首次使用的 QQ 用户，我希望订阅成功时自动创建通知目标，以便无需先执行 `/bind`。
3. 作为 QQ 用户，我希望无需管理员授予命令权限即可订阅有效直播间，以便自主选择关注对象。
4. 作为 QQ 用户，我希望同时订阅多个直播间，以便关注多位主播。
5. 作为 QQ 用户，我希望与其他用户订阅同一个直播间，以便分别收到通知。
6. 作为 QQ 用户，我希望重复订阅不会产生重复关系或重复推送，以便安全重试命令。
7. 作为 QQ 用户，我希望使用长房间号、短房间号或直播链接订阅，以便沿用手头的房间标识。
8. 作为 QQ 用户，我希望同一房间的不同输入形式被识别为同一直播订阅，以便避免重复。
9. 作为 QQ 用户，我希望无效房间或验证失败时获得明确反馈，以便修正输入或稍后重试。
10. 作为 QQ 用户，我希望订阅失败不留下新建的空通知目标，以便避免无效配置。
11. 作为 QQ 用户，我希望通过不带参数的 `/bilibili` 查看自己的直播订阅，以便确认接收范围。
12. 作为 QQ 用户，我希望通过 `/unbilibili 房间号` 取消自己的单个直播订阅，以便停止接收该房间通知。
13. 作为 QQ 用户，我希望取消自己的订阅不影响其他用户，以便独立管理关注范围。
14. 作为 QQ 用户，我希望退订后停止对应的待发送及待重试通知，以便不再收到积压提醒。
15. 作为 QQ 用户，我希望通过 `/unbind` 删除整个通知目标及其全部订阅，以便完整退出服务。
16. 作为 QQ 用户，我希望重新绑定或重新订阅不恢复旧配置与旧投递，以便由自己明确选择接收范围。
17. 作为 QQ 用户，我希望订阅已开播房间时得到当前直播状态和链接，以便立即观看且不额外收到当前场次推送。
18. 作为直播订阅者，我希望新场次被发现时收到主播名称、标题、房间号和链接，以便识别直播并直接进入房间。
19. 作为直播订阅者，我希望同一场次重复检查或服务重启不重复生成通知，以便减少打扰。
20. 作为直播订阅者，我希望重启后发现的新场次仍能通知，以便服务恢复后继续使用。
21. 作为直播订阅者，我希望平台开播时间改变时被视为新场次，以便接收平台记录的下一次开播。
22. 作为直播订阅者，我希望接口失败不会被误认为下播再开播，以便避免虚假通知。
23. 作为直播订阅者，我希望临时投递失败时系统只重试我的失败投递，以便其他成功接收者不被重复打扰。
24. 作为直播订阅者，我希望下播、出现更新场次或通知过期后停止旧消息发送，以便避免收到失去时效的提醒。
25. 作为管理员，我希望在现有通知目标界面添加和移除直播订阅，以便代用户配置。
26. 作为管理员，我希望查看订阅中的主播名称和房间号，以便确认配置对象。
27. 作为管理员，我希望查看共享直播间的直播状态、订阅人数、最近检查时间和异常，以便定位未收到通知的原因。
28. 作为管理员，我希望看到永久投递失败，以便识别无法送达的通知。
29. 作为部署者，我希望第一个订阅者加入时开始监控、最后一个退出后停止查询，以便避免为无人订阅的房间消耗请求。
30. 作为现有仓库订阅者，我希望直播订阅不改变仓库订阅和共享 Issue 追踪，以便继续接收原有通知。
31. 作为部署者，我希望直播查询和积压不阻塞 QQ 心跳或 GitHub 监控，以便外部异常不会拖垮现有服务。
32. 作为部署者，我希望重启后保留直播订阅、场次状态与投递结果，以便避免配置丢失和重复广播。

## Implementation Decisions

- **通知目标与身份**：沿用现有 QQ 私聊通知目标，以 `user_openid` 标识；QQ 号备注仅用于人工识别，不作为身份或投递地址。不引入独立账户或群聊目标。
- **共享领域关系**：通知目标与直播间通过直播订阅形成多对多关系。后台和 QQ 命令使用同一套订阅能力，直播订阅独立于仓库订阅和追踪命令权限。
- **命令契约**：`/bilibili 房间号` 为发送者本人添加订阅；`/bilibili` 列出本人的直播订阅；`/unbilibili 房间号` 取消本人的单个订阅。任何能私聊机器人的用户均可使用。重复添加幂等，不生成额外关系或推送。
- **自动创建与验证**：新增订阅前验证房间。验证成功后才保存订阅，并在需要时创建通知目标；不存在或接口验证失败时明确返回失败，不留下新增订阅或新建的空通知目标，不影响已有配置。
- **输入归一化**：后台和命令均接受数字长号、短号和 `https://live.bilibili.com/房间号` 链接；统一解析为真实房间号，用真实房间号作为共享房间及订阅去重依据。主播 UID 不是有效的房间输入；取消订阅也使用一致的房间身份解析。
- **直播监控生命周期**：不设管理员预先维护的直播间准入池。第一个订阅者加入时建立共享监控，最后一个退出后停止查询。再次订阅按首次订阅规则建立基线，不恢复旧投递。这与现有无人订阅仍监控的 GitHub 仓库规则分别成立。
- **检查周期**：直播状态每 120 秒检查一次，独立于 GitHub 新建 Issue 与 Issue 追踪周期。本期不新增直播检查间隔的后台配置需求。
- **Bilibili 访问能力**：增加统一的房间解析与直播快照能力，获取真实房间号、主播名称、标题、直播状态及平台开播时间。公开接口实测无需登录凭据即可查询，但不视为官方稳定性保证。仅明确的直播中状态触发开播通知，轮播与未知状态不触发；失败或未知状态不能被当作确认下播。
- **场次身份与去重**：直播场次由真实房间号与平台开播时间标识，同一场次重复检查或重启不重复生成通知。即使未观察到下播，只要平台开播时间改变，也视为新场次；断流重连若被平台记为新开播时间，允许再次通知，不增加下播时长阈值。
- **首次订阅**：房间已在直播时，仅在命令回复或后台结果中反馈当前状态与链接，不为新订阅生成当前场次推送；不得因此抑制其他已有订阅者应得的通知。
- **重启恢复**：持久化最后成功的直播观察、场次识别及投递结果。恢复后此前离线但当前已开播的房间可发现新场次；此前已通知且仍为同一场次时不重复通知；开播时间改变时可发现新场次。已有未完成投递继续受原过期时点约束，重启不重置时效。
- **接口失败**：已订阅房间查询失败时保留上次成功状态，记录异常并在后续检查重试，不自动退订，不把失败作为下播。查询恢复到同一场次不制造假开播。
- **接收范围**：发现新场次并保存通知时确定接收者，仅包含当时有效的直播订阅。后来加入者不补发当前场次；退订后重新订阅不恢复旧投递。场次、接收者快照与后续重复处理须保持一致，避免并发订阅和检查改变历史接收范围。
- **投递数据**：直播场次与开播通知独立表达，不伪装为 GitHub Issue。新增必要的共享直播间状态、直播订阅、场次通知及逐接收者投递记录，沿用现有持久化和 QQ 发送能力；迁移不得丢失既有通知目标、仓库订阅、追踪或投递状态。
- **发送内容**：纯文字开播通知包含主播名称、直播标题、房间号和直播链接；标题变化和下播不单独通知。
- **重试与失败**：每个接收者独立保存发送结果。临时失败在 30 秒后重试，成功者不因其他目标失败而重发；永久失败停止自动重试，并在后台可见。
- **通知时效**：系统发现开播超过 10 分钟、确认已经下播或发现更新场次时，取消旧场次尚未发送及待重试的投递。10 分钟从系统发现该场开播开始计算，而非从平台开播时间开始计算。异常查询本身不能作为下播依据。
- **退出与竞态**：取消直播订阅取消该关系全部未完成投递；`/unbind` 或后台删除整个通知目标，清除全部直播订阅及其未完成投递，并保持原有仓库退出语义。取消操作不影响其他目标。发送前复核订阅及投递有效性；已经提交给 QQ 的请求仍可能到达。
- **后台交互**：通知目标编辑界面支持添加房间输入、展示主播名称与真实房间号、移除直播订阅；提供共享直播间列表，显示直播状态、订阅人数、最近检查时间和异常，并展示永久投递失败。复用现有管理鉴权和写请求保护。
- **运行边界**：房间验证与查询采用异步外部请求，不阻塞 QQ WebSocket 心跳；慢查询及直播投递积压不阻塞现有 GitHub 监控。保持现有 QQ 发送节流约束，不因增加直播投递破坏发送节奏。

## Testing Decisions

- 用户已确认测试范围：以现有集成测试为主要入口，从后台 API 或 QQ 命令操作真实临时数据库，用本地模拟 Bilibili 和 QQ 接口验证最终行为，补充后台页面行为测试；自动测试不依赖真实外部服务。
- 好的测试断言用户可见结果、接收者范围、消息内容与持久化恢复行为，不锁定内部函数拆分、SQL 实现或表结构。优先在一次完整“订阅—查询—投递—退订”流程覆盖模块协作，避免为每个内部模块新建测试接缝。
- 复用已有管理 API 集成测试方式：临时 SQLite、真实本地 HTTP 服务、管理员登录会话以及管理请求保护。验证后台与命令看到同一份直播订阅，未授权管理请求仍被拒绝。
- 复用现有 QQ 命令测试的本地 WebSocket 与 HTTP 模拟方式，验证发送者身份隔离、命令回复、自动创建、重复命令和慢查询期间心跳不中断；回复发送失败不得回滚已成功保存的订阅。
- Bilibili 外部接口通过可替换端点或等价的统一外部边界接入本地模拟服务；优先复用项目现有外部来源注入模式，只在需要处增加统一的房间解析与直播快照边界，不为内部查询步骤逐一增加测试接口。
- 验证数字长号、短号和链接归一化到同一直播订阅；验证无效输入、不存在房间、接口失败不会留下新增订阅或空通知目标。
- 验证多个通知目标订阅同一直播间时共享监控，并分别获得一次开播通知；取消一个订阅不影响其他用户，最后一个退出后停止查询。
- 验证首次订阅已直播只反馈状态和链接，后来加入、退出再加入不追加旧场次投递；既有订阅者仍按发现时的范围获得通知。
- 使用可控时间验证 120 秒检查周期和 30 秒重试，不通过长时间真实等待测试时间规则。
- 验证持续同一场次、相同场次的离线再上线、查询失败再恢复不重复生成通知；开播时间改变，即使未采样到下播，也能通知新场次；轮播及未知状态不触发开播。
- 通过关闭并重新打开真实临时数据库模拟重启，验证订阅、场次与投递持久化，成功者不重复投递；新场次可被发现，未完成通知仍按原发现时间过期。
- 验证部分投递失败只重试失败目标；永久失败可见且不自动重试。验证发现后超过 10 分钟、确认下播、新场次、退订和删除目标分别阻止旧投递继续发送。
- 在发送排队和退订交错时验证取消有效，在接口失败时验证不会把失败误作下播；不要求撤回已经提交给 QQ 的请求。
- 复用管理页面 DOM/网络边界测试，验证添加与移除、主播名称和房间号展示、空状态、错误反馈、最近检查状态及永久失败展示，外部文本按普通文本呈现。
- 回归现有仓库订阅、Issue 追踪、QQ 命令、管理鉴权与数据库迁移行为，确认直播功能不改变其接收范围或生命周期。

## Out of Scope

- QQ 群聊推送、其他消息平台、以普通 QQ 号码代替 `user_openid` 绑定。
- 主播 UID 订阅、Bilibili 账户登录、关注列表导入、付费或登录态直播访问。
- 下播、轮播、标题变化、直播内容或回放通知；图片、封面和富媒体消息。
- 新增仓库自助订阅命令、改变仓库监控生命周期或 Issue 追踪权限。
- 要求管理员预先添加直播间的全局准入池。
- 基于断流时长合并平台记录的新场次、人工维护节目场次。
- 补获采样间隔或停机期间已结束的直播、完整历史回溯和旧场次手动补发。
- 对外部 Bilibili 接口稳定性、两分钟内必达、QQ 端严格恰好一次送达的保证；已提交的消息不支持撤回。
- 新增直播检查周期配置界面、正式环境部署与外部平台权限配置。

## Further Notes

- 三轮需求决策均已由用户逐项确认；用户随后调用 to-spec，要求直接综合并发布正式规格。测试范围也已单独确认。本规格标记为 ready-for-agent；后续用户通过 implement 授权实施，五张工单已实现并完成双轴复审，未部署线上。
- 领域术语沿用根术语表：通知目标、直播订阅、直播场次、开播通知、通知投递。ADR 0007 记录订阅驱动的共享直播监控；ADR 0005 的仓库监控规则保持独立。
- 两分钟采样可能漏掉两次检查之间已结束的短直播；停机期间已结束的直播不能通过当前状态查询补获。用户已接受此边界。
- 平台改变断流重连后的开播时间可能引起新场次通知；用户已接受该场次判断规则。
- 公开接口当前实测无需登录 Cookie 或 API Key，但没有取得官方稳定性或限流承诺；测试应覆盖接口异常，实际部署需验证网络可达性和 QQ 的消息投递限制。
