# 03: QQ 自助管理直播订阅

**What to build:** 能私聊机器人的 QQ 用户通过命令管理自己的直播订阅，无需管理员授权或先执行绑定；后台和命令操作同一份订阅。

**Blocked by:** 01 — 后台管理直播订阅。

Status: ready-for-agent
Implementation: complete

- [x] `/bilibili 房间号` 为命令发送者本人添加直播订阅，任何能私聊机器人的用户都可使用，不复用 Issue 追踪命令的授权限制。
- [x] 沿用 `user_openid` 识别通知目标，QQ 号备注不作为投递地址；成功订阅时按需自动创建通知目标，不要求先 `/bind`。
- [x] 接受与后台一致的数字长号、短号及直播链接，按真实房间号去重；重复订阅不新增关系或改变原有配置。
- [x] 输入无效、房间不存在或验证接口失败时明确回复失败，不留下新订阅或新建的空通知目标；已存在的目标和配置不受影响。
- [x] 不带参数的 `/bilibili` 列出本人直播订阅及可识别的主播名称和房间号，未订阅时明确回复空状态，不泄露其他用户配置。
- [x] `/unbilibili 房间号` 取消本人的单个订阅，使用一致的房间身份解析，不影响其他用户；明确反馈取消结果或当前未订阅。
- [x] 首次订阅已开播房间只回复当前正在直播及链接，不生成当前场次推送；重复命令不能改变既定接收者范围。
- [x] `/unbind` 删除整个通知目标、备注、仓库订阅和直播订阅；重新绑定不恢复旧关系。投递能力接通后，删除关系同时取消对应未完成投递。
- [x] 命令使用与后台共用的订阅能力，后台新增后命令可查询和取消，命令新增后后台可查看和移除。
- [x] 先提交成功的订阅变更再回复；回复发送失败不能回滚已经保存的关系，重复收到命令仍保持幂等。
- [x] 房间验证使用异步外部请求，慢请求期间 QQ 心跳不中断；原有绑定和 Issue 追踪命令行为保持兼容。
- [x] 通过本地 WebSocket/HTTP 模拟与真实临时数据库验证各命令、身份隔离、失败无残留、回复失败后的持久化、慢查询心跳，以及后台和命令的交叉操作。

## Scope Notes

本工单可在 01 后与 02 并行实施。命令管理订阅的验收不以监控发送已接通为前提；投递接通后须沿用同一关系的取消语义，不另建 QQ 专属订阅。
