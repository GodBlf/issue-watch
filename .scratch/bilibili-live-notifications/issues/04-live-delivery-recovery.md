# 04: 投递重试、过期取消与重启恢复

**What to build:** 直播订阅者在临时故障和重启后仍能获得有效开播提醒，成功者不因他人失败而被重复广播；已退订或失去时效的旧提醒停止发送。

**Blocked by:** 02 — 共享监控与开播通知。

Status: ready-for-agent
Implementation: complete

- [x] 各接收者独立保存成功、临时失败、永久失败及后续发送资格；临时失败在 30 秒后重试，只重试失败目标，成功目标不因他人失败重发。
- [x] 永久失败停止自动重试，保留可由后台读取的失败结果和原因，为 05 的诊断展示提供真实状态。
- [x] 从系统发现该场开播起超过 10 分钟后，取消该场尚未发送或待重试的投递；不是按平台开播时间起算，重启不重置截止时间。
- [x] 确认已经下播或发现更新场次时取消旧场次全部未完成投递；轮播、未知和异常状态不能被随意推断为一次新开播，查询失败不能当作确认下播。
- [x] 取消单个直播订阅、删除整个通知目标时取消对应未完成投递；重新订阅或绑定不恢复旧投递，其他用户不受影响。取消与查询入口不必依赖 QQ 命令实现。
- [x] 排队和发送前复核关系及投递有效性，验证退订与发送、下播与重试、新场次与旧投递交错的情况；不要求撤回已经提交给 QQ 的请求。
- [x] 关闭并重开数据库后保留订阅、最后成功状态、直播场次和投递结果；同一场次不重新生成通知，已有未完成投递按原有接收范围及期限恢复。
- [x] 恢复后此前离线、当前已开播时可发现新场次；重启前后均直播中但开播时间改变时也可发现新场次；同一场次已成功通知者不再发送。
- [x] 查询失败时保存异常并保留最后成功状态，后续继续检查且不自动退订；恢复为原场次不会生成假开播。失败不延长旧通知时效。
- [x] 新订阅验证、共享检查及重启恢复交错时，既不向后来加入者补发旧场次，也不丢失原有订阅者应得的新场次通知。
- [x] 通过后台配置、可控时间、本地 Bilibili/QQ 模拟和真实数据库重开验证部分失败、30 秒重试、10 分钟过期、下播、新场次、退订及恢复的完整流程。
- [x] 验证失败重试和直播积压不阻塞 GitHub 监控与 QQ 心跳，且不破坏既有发送节流；回归仓库订阅、Issue 追踪及旧通知投递行为。

## Scope Notes

只保证同一已识别场次不重复生成通知，以及独立记录投递结果；不承诺 QQ 网络不确定情况下严格恰好一次到达。不补获采样或停机期间已经结束的直播，不提供旧场次手动补发。
