# 02: 共享监控与开播通知

**What to build:** 管理员配置直播订阅后，系统每两分钟共享检查直播间，发现新直播场次时向当时的订阅者分别发送纯文字开播通知；无需逐用户重复查询。

**Blocked by:** 01 — 后台管理直播订阅。

Status: ready-for-agent
Implementation: complete

- [x] 为有有效直播订阅的房间接通实际运行的共享监控，每 120 秒检查一次，独立于 GitHub 新建 Issue 和 Issue 追踪周期；不增加后台周期配置需求。
- [x] 首个订阅激活共享监控，最后一个退订后停止查询；无管理员预先维护的直播间准入池。
- [x] 使用真实房间号和平台开播时间识别直播场次；重复检查同一场次不重复生成开播通知，同场次曾离线后再次出现也不重复生成。
- [x] 开播时间改变时视为新场次，即使未观察到下播；平台将断流重连记录为新开播时间时允许通知，不设置额外下播时长阈值。
- [x] 仅明确的直播中状态触发开播通知；轮播及未知状态不触发。失败或未知状态不得误作确认下播，不改变上次成功的有效直播观察。
- [x] 发现新场次并保存通知时确定接收者。每个有效订阅者有独立持久化投递结果，成功发送包含主播名称、直播标题、真实房间号及直播链接的纯文字消息。
- [x] 首次订阅已直播房间只反馈当前状态与链接，后来加入者不补发已存在场次；新订阅获取快照不得抑制原订阅者本应获得的新场次通知。
- [x] 订阅新增、移除与检查交错时，接收者范围与场次保存一致；已退订者的待发送记录不再发送，重新订阅不恢复旧投递。
- [x] 持久化直播观察、场次和发送结果，正常数据库重开后可识别已处理场次；不把直播场次塞入 Issue 通知模型。
- [x] 外部直播请求或发送积压不阻塞 QQ WebSocket 心跳与现有 GitHub 监控，继续遵守现有 QQ 发送节奏。
- [x] 使用本地模拟 Bilibili 和 QQ、真实临时数据库及可控时间，验证后台订阅到最终消息的完整路径、120 秒周期、多用户共享检查、首次订阅基线、场次去重和最后一人退订停止查询。

## Scope Notes

本工单交付共享检查与成功投递的完整路径，并建立持久化及基本取消行为。失败重试、全部失效条件、恢复与竞态的完整验收由 04 补齐；后台诊断展示由 05 完成。
