# 03: 按独立间隔广播新评论并可靠投递

**Status:** ready-for-agent
Implementation: complete



**What to build:** 被追踪 Issue 出现新评论后，服务按独立配置检查并广播摘要，后台可配置间隔、查看检查异常，失败恢复不会丢失已发现动态。

**Blocked by:** 02：后台添加、查询和取消共享 Issue 追踪

- [x] 新增独立追踪检查间隔，默认 300 秒，范围 1–86400 秒；后台设置分别展示两种间隔的保存及实际生效状态。
- [x] 保存后无需重启，从保存时重新计时；当前检查完成，不启动重叠检查；配置冲突及加载失败有明确反馈。
- [x] 仅获取追踪起点后的评论，正确处理分页；无变化不通知，同轮同一 Issue 的动态合并。
- [x] 摘要包含仓库、编号、标题、类型、操作者、评论节选及链接；过长内容截断，过多动态显示总数及有限摘要，遵守实际消息发送限制。
- [x] 动态不经过新建 Issue 筛选规则；发现时确定接收者，按订阅独立保存投递及重试。新订阅不补历史，退出订阅取消自己的未发送投递。
- [x] 手动取消追踪取消该次追踪未发送投递；已发出请求可能送达，取消后重添不恢复旧积压。验证取消与检查、投递并发的边界。
- [x] 持久化动态去重及成功检查进度；服务或查询故障恢复后补查，避免部分查询失败提前推进进度，成功接收者不因其他接收者失败而重复广播。
- [x] 单个 Issue 失败不影响其他追踪；不存在或不可访问时保留追踪并展示异常，不当作关闭。无订阅者仍检查且不向后来订阅者补历史。
- [x] 通过可控 GitHub/QQ 输入验证定时检查、分页、重启补查、故障隔离、去重、投递重试和后台配置交互。
