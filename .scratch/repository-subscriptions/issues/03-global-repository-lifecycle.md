# 03: 全局仓库移除同步清理个人订阅

Status: ready-for-agent
Blocked by: 01

**What to build:** 管理员全局移除仓库时，所有通知目标的相关仓库订阅随移除生效一并清除，原有停止监控、取消积压和结束共享追踪行为保持完整。重新加入仓库后明确重新分配用户，不自动恢复旧订阅。

**Blocked by:** 01 — 后台配置仓库订阅，统一按订阅分发。

- [ ] 清除订阅进入启动与热加载共用的全局仓库生效路径，覆盖后台保存和直接配置文件变更，不仅依赖后台移除按钮。
- [ ] 全局移除生效时清除全部通知目标对该仓库的关系，沿用原有停止监控、取消两类积压及终止共享 Issue 追踪的规则。
- [ ] 移除与重新加入遵循现有全局监控周期；重新加入不恢复个人订阅、旧投递或旧追踪，由管理员重新分配，仍不补发停监期间创建的 Issue。
- [ ] 订阅保存使用实际生效仓库池，与全局移除协调；两操作竞争后不能留下针对已移除仓库的有效订阅，失败操作不能部分保存。
- [ ] 后台明确沿用配置已保存与已生效的区别，保存未生效的新增仓库不能提前成为有效个人订阅；界面面对失效选择提供明确反馈。
- [ ] 仓库大小写编辑不视为删除再加入，保留订阅、监控周期和进度；新增仓库不自动分配给已有用户。
- [ ] 无人订阅仍保持全局监控、历史发现和共享追踪；个人取消订阅与全局移除保持不同语义。
- [ ] 启动按最终配置对账，未观察到的中间删除再加入继续沿用既有生命周期约束；不得假定能够恢复停机期间所有中间变化。
- [ ] 使用真实管理 API、配置热加载和启动对账场景验证清理及重新加入，通过模拟发现/追踪及 QQ 发送确认不会恢复旧消息；覆盖订阅保存竞争、其他仓库不受影响和大小写身份。

## Scope Notes

沿用 ADR 0004 的全局生命周期机制，补齐仓库订阅的联动；不重新设计全局仓库配置来源、不停止无人订阅仓库。该工单不依赖 02 的专项在途竞争补强，也不依赖 04 的高级选择操作。
