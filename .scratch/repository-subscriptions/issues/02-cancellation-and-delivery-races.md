# 02: 取消订阅可靠停止积压与重试

Status: ready-for-agent
Implementation: complete
Blocked by: 01

**What to build:** 管理员取消通知目标对某仓库的订阅后，该目标相关旧积压可靠停止；取消与发送并发、重新订阅、人工重试和服务重启均不能复活旧投递。已经提交 QQ 的请求保留真实结果，其他用户与仓库继续正常发送。

**Blocked by:** 01 — 后台配置仓库订阅，统一按订阅分发。

- [x] 从真实后台保存完整仓库清单触发取消，订阅变更和相关积压取消原子生效，新建 Issue 与追踪动态采用一致语义。
- [x] 订阅取消和发送领取确定先后，保存成功后不得再领取被取消的旧投递；不得仅依赖先读取关系、随后异步发送的非原子检查。
- [x] 已开始的 QQ 请求可能完成，成功结果准确记录；取消后失败不再重试。网络请求不占用数据库事务，沿用既有至少一次可靠性边界。
- [x] 待发送、待重试及可人工重试失败投递取消后，人工重试不能重新激活；已发送历史保留且不重复发送。
- [x] 快速取消再订阅不因当前订阅关系重新存在而恢复旧投递；以后新发现的事件仍正常发送。
- [x] 重启不恢复已取消积压，包括崩溃遗留在途状态的恢复路径；普通打开数据库连接不额外触发发送恢复。
- [x] 取消不阻断其他用户、其他仓库，也不终止共享 Issue 追踪；取消批次不应继续作为有效积压拖延正常工作。
- [x] 使用已有真实管理 HTTP 入口和可控 QQ 发送替身，针对两类通知覆盖取消先于领取、领取先于取消、在途成功和失败、快速重新订阅、人工重试与重启，不依赖真实等待或内部调用顺序断言。
- [x] 保留独立接收者失败重试行为：失败目标的重试不导致已成功目标重复接收。

## Scope Notes

依赖 01 的基本订阅与取消能力，补强跨请求、队列和重启的完整行为；若已有机制已满足场景，复用并补齐行为验证，不无故重写。页面状态和健康统计展示由 04 负责，整体交付应保持一致。
