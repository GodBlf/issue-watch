# 按通知目标管理仓库订阅

Status: ready-for-agent

## Problem Statement

当前所有 QQ 通知目标接收相同监控仓库的新建 Issue 与共享 Issue 追踪动态，管理员无法为不同用户配置不同的接收范围。用户因此收到自己不关注的仓库消息。现有后台只能管理通知目标及全局仓库，不能建立二者的独立订阅关系。

## Solution

保留全局监控仓库池、共享抓取和共享 Issue 追踪清单，在后台为每个通知目标管理仓库订阅。新建 Issue 和追踪动态仅发送给发现入库时订阅对应仓库的通知目标。升级一次性保留已有接收范围，之后新增用户与新增仓库均不自动建立订阅。本期由管理员操作，用户通过 bot 自行管理仓库订阅留待后续。

## User Stories

1. As an 管理员, I want 为不同通知目标选择不同仓库, so that 每个人只接收关注范围内的消息。
2. As an 管理员, I want 为同一通知目标选择多个仓库, so that 一个用户可以关注多个项目。
3. As an 管理员, I want 将同一仓库分配给多个通知目标, so that 多个用户可以共同关注一个项目。
4. As an 管理员, I want 沿用现有 QQ 私聊通知目标, so that 无需另建用户登录账户。
5. As an 管理员, I want 通过 QQ 号备注识别通知目标, so that 不必依靠难以识别的投递标识操作。
6. As an 管理员, I want 在现有列表查看订阅数量与仓库, so that 能直接检查每个人的接收范围。
7. As an 管理员, I want 从全局仓库池多选仓库, so that 分配范围与实际监控范围一致。
8. As an 管理员, I want 在仓库选择器中搜索仓库, so that 仓库较多时仍能快速配置。
9. As an 管理员, I want 全选仓库, so that 可以快速配置需要接收全部当前仓库的用户。
10. As an 管理员, I want 清空仓库选择, so that 可以保留用户但停止其全部通知。
11. As an 管理员, I want 一次保存完整仓库清单, so that 不会出现只保存部分修改的状态。
12. As an 管理员, I want 明确看见空订阅状态, so that 能理解用户为何没有收到通知。
13. As an 通知接收者, I want 新建 Issue 仅按仓库订阅分发, so that 不再接收其他仓库的广播。
14. As an 通知接收者, I want 评论、引用、关联 PR 和关闭等追踪动态遵循同一范围, so that 所有通知来源的规则一致。
15. As an 通知接收者, I want 订阅后接收系统新发现的消息, so that 不遗漏创建稍早但尚未被发现的 Issue。
16. As an 通知接收者, I want 订阅时不补发系统已发现的历史消息, so that 不会突然收到历史积压。
17. As an 通知接收者, I want 取消仓库订阅后取消相关待发送和待重试消息, so that 取消可以停止后续排队投递。
18. As an 通知接收者, I want 取消某仓库不影响其他仓库的通知, so that 我的其他关注继续正常工作。
19. As an 通知接收者, I want 他人取消订阅不影响我的接收, so that 用户之间的订阅相互独立。
20. As an 通知接收者, I want 重新订阅不恢复已取消的投递, so that 不会重新收到旧积压。
21. As an 管理员, I want 无人订阅时仍继续全局监控和共享追踪, so that 个人选择不会改变全局监控生命周期。
22. As an 现有通知接收者, I want 升级后仍订阅当前全部监控仓库, so that 升级不意外中断原有接收范围。
23. As an 管理员, I want 升级不重发已经成功的通知并保留正常未完成投递, so that 数据迁移不会制造重复或丢失积压。
24. As an 管理员, I want 后续新增仓库不自动分配给任何已有用户, so that 用户的范围始终是明确选择的结果。
25. As an 新通知接收者, I want 首次绑定从空订阅开始, so that 管理员可以有针对性地配置我的范围。
26. As an 已绑定通知接收者, I want 重复绑定保留原配置, so that 重复命令不会清空订阅。
27. As an 管理员, I want 后台新增通知目标也从空订阅开始, so that 两种创建方式行为一致。
28. As an 通知接收者, I want 解绑删除全部仓库订阅并取消未完成投递, so that 可以完全退出通知。
29. As an 通知接收者, I want 重新绑定不恢复旧订阅或投递, so that 重新加入是明确的新开始。
30. As an 管理员, I want 全局移除仓库时清除所有相关个人订阅, so that 停止监控不会留下隐式恢复的配置。
31. As an 管理员, I want 全局重新加入仓库后手动分配用户, so that 新监控周期不会自动恢复旧接收范围。
32. As an 有追踪命令权限的用户, I want 继续管理共享追踪而无需先订阅该仓库, so that 原有管理授权保持独立。
33. As an 管理员, I want 重启保留已保存的仓库订阅, so that 不必重新配置。
34. As an 管理员, I want 保存失败或仓库已被移除时看见明确反馈, so that 不会误以为订阅修改已经生效。
35. As an 管理员, I want 了解已提交 QQ 的请求可能仍送达, so that 能正确判断取消生效边界。

## Implementation Decisions

- 通知目标继续以 QQ `user_openid` 标识，保留现有目标身份与 QQ 号备注；备注不能作为绑定凭据或投递地址。通知目标与仓库订阅是不同关系，空订阅不能被视为“订阅全部”。
- 持久化通知目标与监控仓库之间的多对多关系，同一关系唯一。仓库标识沿用现有 `owner/name` 校验和大小写不敏感身份规则，不为每个用户复制抓取进度或 Issue 记录。
- 扩展现有后台通知目标列表和管理接口，提供每个目标的完整仓库清单；提供一次替换完整清单的写操作，接受空清单，验证目标存在、仓库属于当前生效的全局仓库池。保存订阅与取消相关积压必须原子生效；非法输入或过期目标不能产生部分修改。沿用现有管理写入校验，不引入新的登录系统。
- 后台继续显示和编辑 QQ 号备注，在用户列表显示仓库与订阅数量。仓库选择支持多选、搜索、全选和清空；全选指当前全局仓库池，搜索只改变可见项，不能悄悄丢弃隐藏选择。一次保存完整清单，明确显示“未订阅任何仓库”、保存进度和失败信息。
- 新建 Issue 与所有追踪动态共用仓库订阅接收范围。保持发现记录全局去重，在发现入库的事务中确定接收目标并建立独立投递；新订阅不会为此前已经发现的事件新增投递。Issue 创建时间早于个人订阅、但发现入库晚于订阅时可以通知，仍需满足全局监控周期原有基线规则。
- 取消某仓库订阅取消该目标在该仓库的新建 Issue 和追踪动态的未完成投递，阻止旧积压通过人工重试或重新订阅恢复。保留已发送历史。取消不改变其他用户、其他仓库、全局抓取和共享 Issue 追踪。
- 沿用现有发送领取与取消协调机制：保存取消与开始发送确定先后，保存成功后不得再领取已取消订阅的旧投递。网络请求不占用数据库事务；已提交 QQ 的请求可能完成，真实结果应记录，取消后的失败不得再次重试。重新订阅只影响未来新发现的事件，不能让已取消的旧投递因当前关系重新存在而复活。
- 沿用每个接收目标独立投递状态与失败重试，一人的失败不能向已成功接收者重复发送。沿用既有投递可靠性边界，不新增跨 QQ 与数据库的恰好一次承诺。
- 升级迁移仅执行一次：为迁移前已有通知目标建立当前全部生效监控仓库的显式订阅。保留原目标身份、备注、去重记录、已完成投递及仍有效的未完成投递，不对历史发现重新分配接收者。需兼容现有旧单人绑定迁移链路；先落实最终有效全局仓库范围，再建立订阅，避免授予已移除仓库。
- 迁移有持久化完成标记，重启或重复打开数据库不会重新订阅已被取消的仓库，也不会给升级后新增的用户或仓库自动授权。没有旧目标的安装保持空订阅。
- `/bind` 新建空订阅通知目标，重复调用幂等且保留配置；后台手动新增目标行为一致。`/unbind` 以及后台删除目标删除其仓库订阅和 QQ 号备注，取消全部未完成投递；重新加入使用新目标身份且为空订阅。命令回复应准确传达绑定后仍需管理员配置仓库的状态。
- 全局配置仍是监控仓库池的来源，订阅不修改全局配置；无人订阅也继续抓取、记录和维护共享追踪。保留现有全局仓库数量与格式限制。
- 全局仓库移除实际生效时，清除所有目标的相关订阅，并按既有生命周期规则停止监控、取消积压、终止共享追踪。清除须进入启动与热加载共用的生效路径，不能仅在后台按钮处理。重新加入开启新周期且不恢复个人订阅；大小写编辑不视为移除再加入。
- 继续区分全局配置已保存与已生效；仓库订阅保存以实际生效仓库池校验，与全局移除协调，避免移除后出现残留有效订阅。运行期间未观察到的中间配置变化仍沿用既有最终配置对账规则。
- 共享 Issue 追踪不增加用户归属。`/track`、`/untrack` 分别授权，授权与仓库订阅独立；有权限但未订阅仓库的用户仍可管理该仓库追踪，本人是否收到动态由仓库订阅决定。
- 根据新概念更新后台与使用说明，避免继续暗示所有用户接收相同仓库。健康统计应区分“存在通知目标”与“该目标存在仓库订阅”，取消投递不能继续显示为待发送积压。

## Testing Decisions

- 只测试可观察的行为与状态，不断言内部表名、私有调用顺序或 DOM 层级。主要复用真实后台 HTTP 管理入口、现有发现及追踪入口、持久化存储和模拟 QQ 发送，组成集成场景；不为测试新增生产管理端点。页面行为另沿用现有 DOM/网络边界测试。用户已确认此测试边界符合预期。
- 现有先例包括后台管理 HTTP 测试、独立广播投递与重试测试、共享 Issue 追踪测试、仓库生命周期及配置热加载测试、QQ 命令测试，以及执行真实管理脚本的 DOM/网络测试。优先扩展这些已有 fixture 和替身，不建立重复测试框架。
- 接收范围矩阵：甲订阅 A、乙订阅 B、丙订阅 A 与 B、丁为空；通过真实管理请求配置后发现两个仓库的新建 Issue 和追踪动态，模拟 QQ 仅收到预期用户与仓库组合。包括评论、引用、关联 PR 状态与关闭动态，并验证同一事件去重。
- 时间边界：订阅前已发现不补发；创建早于个人订阅但发现晚于订阅可以通知；全局基线之前创建仍不通知；重新订阅不恢复旧投递，但新事件正常投递。
- 取消与发送竞争：取消该用户该仓库的待发送、重试及可人工重试失败投递，其他用户和其他仓库正常；通过可控发送替身验证领取前取消不发送、在途可完成、在途失败不重试，快速取消再订阅不能恢复旧工作。新建 Issue 与追踪动态都需覆盖。
- 迁移与持久化：使用真实旧版数据库 fixture，验证当前仓库全量订阅只授予已有用户一次，已成功不重发、有效积压保留、历史不补发；覆盖无旧目标、旧单人绑定、配置外仓库和重复启动。修改订阅后再次启动，确保取消不被迁移恢复，之后新增目标和仓库保持未订阅。
- 生命周期：全局移除在启动和热加载路径均清除相关订阅、取消积压及结束追踪；重新加入不恢复订阅；大小写变化保持身份；无人订阅仍记录发现及追踪状态，后续订阅不补发这段历史。
- 后台 API：完整清单替换、空清单、非法或已移除仓库、重复仓库规范化、过期目标、写入校验、失败原子性和重启持久化。全局移除与订阅保存竞争后不得残留有效订阅。
- 页面：列表显示、搜索、多选、全选、清空、空订阅、完整清单提交、隐藏选择保留、保存失败和进行中状态；保留用户搜索、分页、备注管理和既有页面导航。用户输入仍以文本安全呈现。
- QQ 命令与权限：首次绑定空订阅、重复绑定保留、解绑取消所有投递、重新绑定不恢复；未订阅仓库但有相应追踪权限仍可操作，无权限者不因订阅获得管理权。
- 旧测试中“绑定即接收全部仓库”的默认假设应改为显式配置订阅，同时保留其独立重试、全局去重、健康状态及生命周期原有断言。

## Out of Scope

- 用户通过 bot 命令查看、添加或删除仓库订阅；本期只适配已有绑定、解绑命令。
- 个人独立 Issue 追踪清单、按用户定制抓取进度或全局监控周期。
- 标题、标签等内容筛选规则，以及用户级筛选配置；术语表存在筛选规则不代表当前已有此实现。
- 用户登录账户、新认证体系、群聊目标，以及以 QQ 号备注代替 OpenID 绑定。
- 从仓库入口批量分配用户的第二套后台界面。
- 历史补发、恢复已取消投递、自动恢复全局重新加入仓库的旧订阅。
- 改变追踪命令授权模型、现有全局仓库配置来源或投递可靠性承诺。
- 实际部署、操作线上用户数据或在本次规格生成中实施业务代码。

## Further Notes

- 本规格综合用户逐轮确认的 Q1–Q11，所有答案均采用推荐方案。架构依据为 ADR 0005；它调整 ADR 0001 的全体共享接收范围和 ADR 0003 的向全体接收者投递，保留独立投递、共享追踪和独立授权，并沿用 ADR 0004 的全局监控周期约束。
- 个人新增订阅按“发现入库时”生效；全局移除后重新监控仍按“新监控周期创建时间基线”筛选。二者不能混同。
- 后续 bot 仓库订阅命令应复用同一仓库订阅操作与取消语义，不维护第二份订阅数据。
- 本工单发布至项目约定的本地 Markdown issue tracker，状态为 `ready-for-agent`；不代表业务功能已实现，也不自动开始代码重构。
