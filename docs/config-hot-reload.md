# 配置热加载设计

目标：运行中增删监控仓库和修改轮询间隔，不重启服务、不改变 QQ 绑定或继续监控的仓库进度。

后台任务每 2 秒重新读取 TOML，以内容比较检测变化，支持原子替换保存。先完整校验，再以单个事务对账仓库启用状态和监控周期，最后通过 watch 通道发布有效配置。移除在接受事务提交后生效，不等待主循环结束：旧抓取响应不能入库或更新游标，未发送与重试投递取消，共享 Issue 跟踪及其积压停止。发送以事务领取为开始边界，已经开始的 QQ 请求可能完成，失败不恢复重试。取消条目立即跳过，节流等待每 100 毫秒检查取消。网络请求不占用数据库写锁。

无效配置继续沿用最后有效值，同一错误只记录一次，配置修复后自动恢复。仓库列表、新建 Issue 轮询间隔和跟踪检查间隔可热加载。数据库路径改变会拒绝整个候选配置，凭据仍在启动时读取。历史发现、已发送及已取消投递保留；重新加入递增监控周期，以接受时间建立新基线并清空旧游标，不补发停监期间的 Issue，不恢复旧跟踪或旧投递。大小写编辑不重设进度。

启动复用仓库对账并恢复崩溃遗留的发送状态。首次升级保留当前配置中旧仓库的进度，配置外仓库停用并取消积压。普通重启保留启用仓库进度；停机期间删除再加回且服务没有接受中间状态时，按最终配置视为连续监控。决策见 ADR 0004。

新周期的时间边界在获得事务写锁后、提交前采样，不使用进入配置接受流程之前的时间，避免 SQLite 等锁期间的 Issue 被补发。

验证在配置文件到监控配置发布的公共边界进行，使用临时文件和真实 SQLite，覆盖原子保存、新增基线、旧进度与绑定保留、无效/缺失配置回退及修复、删除再添加，以及后台配置更新。

管理页面修改使用同一配置文件，先校验并检查读取版本，再通过同目录临时文件替换保存。配置源版本在服务重启后变化，旧页面需刷新后提交。页面分别展示已保存、仓库变更已生效（后台接受）、监控循环已采用配置；接受后立即刷新活跃仓库和队列统计，轮询定时器仍待主循环采用。检测到外部文件变更时拒绝过期覆盖；手动编辑与页面保存应避免同时写入，非协作编辑器在最后一次文件校验与替换之间的竞争无法通过版本检查完全消除。

Docker 本地与生产 Compose 均挂载可写配置目录。页面保存保留文件权限及配置值，Linux 上还保留原属主与属组；TOML 会被重新格式化，原注释不会保留。只读挂载、无权限或文件无效时操作失败，监控继续使用最后有效设置；配置修复后恢复加载。
