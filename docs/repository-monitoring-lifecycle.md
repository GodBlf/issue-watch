# 仓库移除与重新加入修复方案

产品决策见 [ADR 0004](adr/0004-repository-monitoring-lifecycle.md)。方案已确认；使用者已授权实现、提交 PR、合并并触发生产流水线。

## 行为

- 移除仓库停止新建 Issue 抓取，取消该仓库所有广播订阅的未发送与等待重试投递，并停止单独 Issue 跟踪及其未发送投递。
- 重新加入开启新监控周期，只通知加入生效时间之后创建的 Issue；停监期间的 Issue 不补发。
- 保留历史发现、已发送与已取消记录。重新加入不会重启旧跟踪，也不会复活旧投递。
- 保留列表中的其他仓库、订阅、轮询间隔和数据库路径不变。仅改变仓库名称大小写不会开启新周期。
- 已开始的 QQ 请求无法撤回；页面显示移除已生效后，不再开始该仓库的发送。

## 生命周期持久化

monitored_repositories 增加 active 和 generation。generation 表示监控周期的身份，不能仅靠启用状态或时间判断旧请求是否有效。

启动和热加载共用仓库集合对账入口，完整验证配置后，以单个 SQLite 写事务接受变化：

1. 保留的启用仓库维持 baseline、cursor、generation。
2. 移除的仓库设为 inactive，取消 pending/retry 投递，停止相关跟踪并取消其投递。
3. 新仓库建立启用状态；停用仓库重新加入时递增 generation，baseline 设置为本次接受时间，cursor 清空。
4. 事务失败则全部回滚，继续使用最后有效配置；提交成功才发布新配置。

配置变化必须由后台接受路径立即作用于持久化生命周期，不能等待主循环完成全部抓取和整批发送。

## 旧抓取请求隔离

抓取开始只读取启用仓库的监控周期，不通过 ensure_repository 隐式激活仓库。请求携带 generation，每次通知入库和 cursor 更新都在事务内校验 active 且 generation 相同。校验不通过时丢弃旧结果，结束旧抓取。

创建时间必须晚于当前周期 baseline 才可入队。GitHub since 的返回结果不能代替本地创建时间过滤。移除后快速重新加入时，旧请求即使看到仓库再次启用，也因 generation 不同而无法污染新周期。跟踪请求使用对应的取消或周期身份检查，避免停止后旧响应继续生成跟踪投递。

## 发送与移除协调

广播及跟踪的待发送查询排除停用仓库，发送前重新检查投递状态。发送开始和生命周期接受共享短暂的协调边界：明确先登记发送开始，或先让移除生效；移除之后不允许旧批次登记新的发送。网络请求期间不持有 SQLite 写事务或全局协调锁，已登记开始的请求属于在途请求。

在途成功应保存真实发送结果，即使等待期间仓库被移除；失败在移除后不得恢复为待重试。结果更新只能针对本次已开始的投递，不能把其他已取消记录改为 sent。实现时核对既有重启恢复逻辑，并用测试保证新增发送中状态或领取身份不会让重启后的投递永久卡住，也不宣称跨 QQ 和 SQLite 可以保证恰好一次。

已取消的批次条目立即跳过，不逐条睡眠。只对实际发送节流，等待期间每 100 毫秒检查取消，并在发送开始事务中再次校验。其他仓库投递不因取消的大批旧通知而被拖延。

## 状态与管理页面

保留“已保存”状态；“移除已生效”必须在生命周期提交、发送协调和跟踪停止完成之后显示，不依赖主循环消费完旧批次。GitHub 活跃仓库列表与队列统计及时刷新，不显示已取消条目为 pending。保留取消原因用于排查，不作为失败告警。

## 升级与重启

首次迁移对当前配置内的旧仓库保留进度；配置外仓库设为 inactive 并取消未发送投递。不能先把所有仓库都视为停用再重新激活，否则会重置正常仓库的进度。

此后启动执行相同对账，处理停机期间最终配置中的移除或加入。同一启用仓库普通重启不重置 baseline，不丢弃正常积压。停机期间移除又加回、且服务没有接受中间状态时，视为连续监控，不增加操作日志或专用入口。

按现有部署约定停止旧实例并备份数据库后升级；启动后验收失败不自动恢复旧数据库，遵守 ADR 0002。本次使用者已授权合并并触发生产流水线。

## 验证

使用真实 SQLite、固定时间和可控 GitHub/QQ 替身覆盖公共链路，避免只测试孤立字段：

- 3 号移除、7 号重新加入：5 号 Issue 不入队，加入后创建的 Issue 正常发送。
- 移除取消所有订阅的 pending/retry，保留 sent 和历史去重；其他仓库及设置不变。
- 抓取请求未返回时移除，返回后不能入库或推进 cursor；快速重新加入也不能让旧 generation 生效。
- 发送前移除不调用 QQ；请求已开始后移除只允许在途请求完成，成功准确记录，失败不重试。
- 大批取消投递快速跳过；其他仓库的可发送通知及时继续，队列统计更新。
- 单独 Issue 跟踪停止、旧响应不入队、旧跟踪批次取消，重新加入不自动恢复跟踪。
- 配置接受失败整体回滚；大小写编辑和普通重启保留进度；停机删除与首次迁移符合规则。
- 管理页面区分保存与生效，移除生效后没有新的发送开始。
