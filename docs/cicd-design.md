# GitHub Actions 自动构建与服务器部署方案

状态：使用者已要求按 spec 实施；操作步骤见部署文档，实际上线结果以工作流和服务器验收为准。

## 已确认的选择

- `master` 分支检查通过后自动部署；允许单服务器更新时短暂停机。
- GitHub Actions 构建镜像并发布至公开 GHCR，再通过 SSH 调用服务器上的固定部署脚本。
- 首次上线包含安装 Docker/Compose、迁移当前原生服务、保留配置和 SQLite 数据、停止旧 systemd 服务并启用容器。
- 每次更新前停服务并备份 SQLite；新版本启动后验收失败时停止新版本、报告失败，由人工决定是否恢复旧镜像与数据库。
- 使用专用 SSH 部署密钥限制为固定部署入口；QQ/GitHub 运行凭据留在服务器；以本机 `/api/status` 返回成功作为启动验收。

## 实施方案

PR 执行格式检查、Rust 测试和镜像构建验证；`master` 检查成功后发布 `linux/amd64` 镜像到 `ghcr.io/godblf/issue-watch`。部署引用该次构建的不可变镜像摘要，避免服务器误取另一提交的镜像。生产部署串行执行，不中途取消已开始的数据备份或容器切换。

GHCR 包可见性独立于 GitHub 仓库可见性。当前 CLI token 缺少包访问权限；首次发布后需核实包已公开，并验证服务器匿名拉取成功，再进行服务切换。若权限不足，明确报告所需操作。

建立专用部署密钥并保存到 Actions secrets；服务器为该密钥配置固定部署命令并关闭端口转发等能力。部署入口校验目标镜像和参数。Actions 校验 SSH 主机密钥，不跳过主机身份验证。

部署脚本先拉取目标镜像，成功后停止当前服务并备份数据库，再启动新容器。拉取失败时继续运行当前服务；停服务后的准备阶段失败，在数据库尚未被新程序打开的前提下恢复当前服务。新版本启动后的验收失败则停止新容器、保留备份与日志，等待人工恢复决定。

保留宿主机的配置目录、数据目录和运行凭据，通过 Compose 目录挂载与环境变量提供给容器；不将它们复制进镜像。健康端口仅绑定 `127.0.0.1:8081`。验收确认新容器运行且本机 `/api/status` 成功响应；未绑定用户、暂无发送记录或 QQ/GitHub 的业务告警不作为启动失败。

首次迁移先准备镜像、容器环境、配置及部署入口，再停止旧 `issue-watch.service` 并备份数据。容器验收成功后禁用旧服务的自动启动，保留旧二进制和服务定义用于人工恢复。备份暂不自动删除。

## 恢复边界

程序启动可能执行数据库迁移；旧二进制未必兼容新数据库。恢复部署前的备份还可能丢失启动后的进度或投递记录，导致通知重复。因此不在新程序启动后自动回退镜像或恢复数据库。人工恢复前先停容器、检查日志并保存失败后的数据库，再决定使用哪份数据与哪个版本。
