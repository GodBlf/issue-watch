# issue-watch

Rust 服务，按配置轮询 GitHub 公开仓库的新建 Issue，并通过 QQ 官方机器人私聊通知。

## 本机运行

1. 复制 `config.example.toml` 为 `config.toml`，填写 `repositories`。
2. 在 `.env.local` 设置 `QQ_APP_ID`、`QQ_APP_SECRET`，可选设置 `GITHUB_TOKEN` 和 `QQ_ACCESS_TOKEN`。
3. 执行 `cargo run`。

默认每 60 秒检查一次，SQLite 数据保存到 `data/issue-watch.sqlite3`。第一次加入监控的仓库只建立当前时间基线，不推送历史 Issue。

## 配置热加载

运行时直接修改并保存 `config.toml`，无需重启。服务每 2 秒检查文件内容，支持编辑器原子替换保存方式：

```toml
poll_interval_seconds = 60
tracking_interval_seconds = 300
database_path = "data/issue-watch.sqlite3"
repositories = ["GodBlf/mycode-rust", "owner/another-repo"]
```

`repositories` 和 `poll_interval_seconds` 可热加载（间隔范围 1–86400 秒）。新增或重新加入仓库在配置被接受时建立当前时间基线，不补发停监期间的新建 Issue。移除取消该仓库未发送及等待重试的通知，并停止其共享 Issue 追踪；已经开始的 QQ 请求可能仍送达。QQ 绑定和继续监控的其他仓库进度不会重置。

无效 TOML、未知字段、空仓库列表、重复/无效仓库名、无效间隔或文件暂时不可读时，保留最后一次有效配置并记录错误。修正文件后自动恢复加载。数据库路径和环境变量凭据变更需要重启；改变数据库路径的配置会整份拒绝。

配置检查独立于 GitHub 请求运行，监控任务在当前轮询/投递完成后使用新设置；已经开始的请求不会取消。配置更新后立即开始下一轮检查，之后使用新的间隔。

Docker Compose 挂载可写配置目录，`ISSUE_WATCH_CONFIG` 指向 `/app/config/config.toml`。管理页面保存与宿主机编辑器的原子替换都能被热加载识别。目录和文件须允许容器运行用户写入；不要只挂载单个配置文件。

## Docker

生产环境的 GitHub Actions 镜像发布、首次迁移和恢复步骤见 [自动构建与部署](docs/deployment.md)。生产部署保留宿主机回环健康端口 8081，本地 Compose 的默认端口仍为 8080。

将配置放入 `config` 目录并填写仓库，然后通过环境变量提供凭据：

```powershell
New-Item -ItemType Directory -Force config
Copy-Item config.example.toml config/config.toml
docker compose up -d --build
```

Compose 将 `./data` 挂载为持久化目录；不要把 `.env.local` 复制进镜像。已有本地 Compose 部署先停止容器，把原 `config.toml` 复制到 `config/config.toml`（已有目标文件时先确认并备份），再按新 Compose 重新创建容器；原生运行仍默认读取根目录的 `config.toml`。

## 健康状态网页

管理页面和 `/api/status` 现在都要求管理员登录。生产环境使用可信 IP 证书访问 `https://172.197.176.142/`，安装、密码初始化、续期和恢复步骤见 [公网管理员入口](docs/public-admin.md)。服务重启后登录保留，每次登录固定有效 365 天，退出撤销当前会话，SSH 重置密码撤销全部会话。

原生服务默认监听 `127.0.0.1:8080`，通过 `ISSUE_WATCH_HEALTH_BIND` 配置；Compose 仍只发布宿主机回环端口，生产为 8081、本地默认为 8080，不应将应用直接发布到公网。无需登录的内部健康检查改为 `/internal/status`，公网代理必须拒绝整个 `/internal/` 前缀。

本地开发可在 `.env.local` 设置 `ISSUE_WATCH_ADMIN_ORIGIN=http://localhost:8080`，执行 `cargo run -- --admin-password` 初始化密码，再运行服务并用 `http://localhost:8080/` 登录；HTTP 仅允许回环 Origin，Secure Cookie 依赖浏览器对 localhost 的处理。生产始终使用 HTTPS。默认 Origin 为 `https://127.0.0.1`，部署时必须显式配置实际入口。

页面每 10 秒刷新，显示程序运行时长、逐监控仓库的检查结果、QQ 连接/绑定/鉴权/实际发送状态及通知队列。尚无必要检查结果时为未知；偶发检查失败、未绑定或通知重试为警告；同一仓库连续三次失败、已知 QQ 鉴权失败、永久发送失败或业务卡住为异常。无新建 Issue、无发送记录本身不算故障，没有发送结果会标记未验证。

业务正在检查或投递时，超过 `max(3 × 当前轮询间隔, 5 分钟)` 没有推进判为卡住；正常等待下一轮不会误报。GitHub 和 QQ HTTP 请求总超时为 30 秒。重启后检查状态重新观察，现有通知队列和绑定数据仍保留。

服务暂时不可达时，已打开页面保留上次数据及时间，整体状态改为未知并显示断连提示；恢复后自动刷新。不可达无法直接区分程序退出、服务器断网和代理故障。服务器不可达时新打开页面可能直接显示浏览器连接错误。

页面支持管理通知目标、共享监控仓库和轮询间隔，不提供手动重试通知、重启操作、主动测试消息、资源监控或历史趋势。

## 管理操作

通过 HTTPS 管理入口登录；全部管理 API 要求有效会话，写请求还需匹配配置的同来源。接收者列表每 10 秒刷新，配置每 2 秒刷新；编辑中的间隔、备注和仓库订阅草稿不会被自动刷新清空。

通知目标可以由管理员填写当前机器人的 `user_openid` 添加，也可以自行 `/bind`。QQ 号备注选填，可修改和清空、不要求唯一、不参与发送。重复添加不覆盖原备注；添加订阅本身不验证 QQ 平台主动发送权限。移除通知目标取消未完成投递并删除全部仓库订阅及备注，已经发出的请求仍可能送达；对方可重新 `/bind`，重新加入不恢复原备注、仓库订阅和积压。

仓库使用 `owner/name` 格式，不允许重复或移除最后一个仓库。新增和重新加入从配置接受时间开始监控；移除取消未发送及重试通知，保留历史去重记录。页面区分“已保存”和“仓库变更已生效”，后者表示该仓库不再开始新的通知发送，已在途请求可能送达。

轮询间隔为 1–86400 秒的整数。页面修改写回同一份 TOML 配置，重启后保留。页面区分“已保存，等待热加载”“热加载已接受，等待当前任务结束”和“监控任务已采用”；保存失败或加载失败明确提示。外部编辑文件或其他页面提交后，过期提交被拒绝，刷新配置后再修改。配置文件无效时须先修正文件，管理接口不会用旧值覆盖它。页面保存会重新格式化 TOML，保留配置值，不保留原注释。

仓库订阅在通知目标列表按人多选，支持搜索、全选当前全局仓库池、清空及一次保存完整清单。搜索保留隐藏选择。空订阅显示“未订阅任何仓库”，不接收任何通知。取消某仓库订阅立即取消该目标相关未完成投递，重新订阅不恢复旧积压，其他用户、仓库和共享追踪不受影响；已经开始的 QQ 请求可能送达。

管理接口为 `GET /api/admin/repositories`（当前生效仓库池）、`PUT /api/admin/subscriptions/{订阅编号}/repositories`（正文 `repositories` 为完整仓库清单，可为空）、`GET/POST /api/admin/subscriptions`、`PATCH/DELETE /api/admin/subscriptions/{订阅编号}` 和 `GET/PATCH /api/admin/config`。写请求携带同来源 `Origin` 与 `X-Issue-Watch-Admin: 1`，JSON 请求还需 `Content-Type: application/json`；配置提交必须携带读取时的 `version`。QQ 号不能替代 `user_openid`；API 结果和页面都不会暴露环境变量凭据。

部署验收：宿主机访问 `http://127.0.0.1:8080/internal/status`（生产端口为 8081），确认 Compose 发布地址为回环；公网验证 HTTPS、匿名管理请求被拒绝、`/internal/` 不可访问及证书续期。完整验收见公网管理员入口文档。健康状态读取不发送 QQ 消息。

## QQ 绑定

启动服务后，任何能私聊机器人的用户都可以发送 `/bind` 创建空订阅通知目标，之后由管理员配置仓库。首次绑定成功回复 `success：已绑定，尚未订阅仓库，请联系管理员配置仓库订阅`；重复绑定回复 `already bound`，不会创建重复订阅。机器人使用触发命令的消息 ID 发送被动回复；回复失败会记录日志，已成功保存的绑定仍然有效。

全局监控仓库池由 `config.toml` 管理，用户只接收发现入库时自己订阅仓库的新建 Issue 与追踪动态。Issue 在个人订阅前创建、订阅后发现仍可通知，但受全局监控周期基线约束。新用户和新添加仓库不会自动建立订阅。新用户不补发已有历史或其他人的积压；无人订阅时仍记录发现进度，但不建立待发送投递。每个接收者独立保存投递状态，发送失败只重试给该接收者，不影响其他人。

发送 `/unbind` 删除通知目标和全部仓库订阅，成功回复 `success`，未绑定时回复 `not bound`。退出取消自己的未完成投递，正在发出的请求可能仍会送达；重新 `/bind` 后从空订阅开始，不恢复之前的积压。

首次升级在全局仓库对账后，为已有通知目标一次性订阅全部当前生效仓库；之后重启不会重新分配已取消的订阅。自动兼容原有单人绑定及投递状态，保留其待发送、重试和失败记录，不重发已成功的通知。没有旧绑定时，升级前的发现记录仅用于去重，不分配给之后加入的用户。数据库变更不支持直接运行旧版本，升级前建议备份 SQLite 数据。

服务保存事件中的 `user_openid`，普通 QQ 号不能直接作为官方发送 API 的目标。机器人处于沙箱模式时，需要在 QQ 开放平台将好友加入测试用户；正式环境仍受平台主动消息权限和发送配额限制。健康网页分别显示通知目标数、已订阅仓库的目标数和仓库订阅关系数，队列数量按“通知 × 接收者”的投递计数，失败记录用订阅编号区分接收者。

`QQ_ACCESS_TOKEN` 可用于直接启动发送适配器；生产环境应由官方 AppID/AppSecret 流程获取并注入短期 token。WebSocket Gateway 的事件连接由 QQ 适配器负责，真实账号权限和主动消息配额需要手工验收。

## Issue 追踪与后台管理

后台按概览、仓库、通知目标、用户权限和设置分开导航；仓库详情中可用完整 Issue URL 添加共享追踪、查看检查时间及异常、取消追踪。列表支持搜索和分页，表单明确保存，自动刷新保留未保存输入。移除仓库前显示当前追踪数量；配置被接受后取消该仓库的新建 Issue 积压、共享追踪及待发送动态。全局移除还会清除全部相关个人订阅，重新加入不恢复旧追踪、旧投递或个人订阅。

Issue 追踪需要配置 `GITHUB_TOKEN`：GitHub GraphQL 时间线用于识别评论、跨仓库引用、明确关联 PR，以及关联 PR 的合并、关闭和重新打开。Token 必须能读取目标仓库及需要关注的关联仓库；无法访问的私有引用和未被 GitHub 识别的文本提及不保证发现。新增追踪不补发历史，追踪数量不设上限；大量追踪可能受到 GitHub 配额限制，查询失败会显示异常并在下一轮重试。

QQ 私聊命令：

- `/track https://github.com/owner/repo/issues/123` 添加共享追踪。
- `/untrack https://github.com/owner/repo/issues/123` 取消共享追踪，影响所有接收者。
- `/tracking` 查询共享清单；`/tracking https://github.com/owner/repo` 按仓库查询。仓库 URL 的 `?page=2` 查询参数用于后续页。

所有 QQ 用户默认没有修改权限，不设 QQ 管理员角色；后台按 `user_openid` 分别授予添加和取消权限，包括未订阅用户。已绑定通知目标或拥有任一修改权限的用户可查询。有权限但未订阅仓库的用户仍可管理共享追踪，但不会收到该仓库动态。解绑不删除权限，撤销权限不取消已有追踪；无权限回复“权限不足：你没有执行此命令的权限，请联系后台管理人员。”。Issue 不存在回复“该 Issue 不存在”。

`tracking_interval_seconds` 默认 300，范围 1–86400 秒，在后台设置中独立修改并热加载，不改变新建 Issue 轮询间隔。启动时执行一次恢复检查，随后按独立间隔检查；无变化不通知，同轮动态按 Issue 合并摘要，发现时按仓库订阅确定通知目标。动态不经过新建 Issue 筛选规则，无订阅者时也检查，不向后来加入者补发。查询或服务故障恢复后补查并去重，投递按接收者分别保存和重试。

追踪开始后的关闭事件自动结束并从当前列表清理，包括未计划处理，以及两轮之间关闭后重新打开的情况。保留最后一批动态和关闭通知供重试；重新打开需重新添加。人工取消撤销该次追踪未发送通知，已经发出的请求可能送达，再次添加不恢复旧积压。

新增管理接口：`GET/POST /api/admin/tracking`、`DELETE /api/admin/tracking/{追踪编号}`、`GET /api/admin/permissions`、`PUT /api/admin/permissions/{user_openid}`。写入沿用本机同源校验；授权正文为 `can_add`、`can_cancel` 两个布尔值。配置接口支持独立的 `tracking_interval_seconds` 字段，仍必须携带配置版本。
